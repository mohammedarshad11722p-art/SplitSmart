### Why this shape
- **Two independent apps, not npm workspaces.** Vercel and Render each just get pointed at a subfolder (`frontend`, `backend`) as the root directory. No shared build tooling to debug at 3am during a hackathon. The cost is that a few TypeScript types (Item, Participant) get duplicated in `frontend/lib/api.ts`; that's acceptable for an MVP.
- **Socket.io lives in the backend, not Next.js.** Vercel runs Next.js as serverless functions that shut down after each request, so they can't hold WebSocket connections open. Render runs a normal long-lived Node process, which is what Socket.io needs.
- **`app.ts` separate from `index.ts`.** Lets tests import the Express app without opening a port.
- **`services/` separate from `routes/`.** Routes deal with HTTP (parse request, send response). Services hold the logic. `split.service.ts` is *pure* (numbers in, numbers out, no database), which makes it easy to unit test.

## Schema: the design choices

The schema is in `backend/prisma/schema.prisma`. It passed `prisma validate`.

```
Bill 1──* Item *──* Participant *──1 Room 1──1 Bill
              (via Claim)
```

1. **Money is integer paise, never Float.** `0.1 + 0.2 !== 0.3` in JavaScript. With floats a ₹1,000 bill split 3 ways can end up ₹0.01 off, and the "totals always match" requirement fails. Storing ₹245.50 as `24550` makes all math exact; we only convert to rupees for display and for the UPI `am=` parameter.
2. **Bill and Room are separate.** The host uploads and edits the bill *before* there is a room, so Bill exists on its own. `Room.billId` is `@unique`, which makes it one room per bill.
3. **Claim is its own table (many-to-many).** An item can be claimed by many people and a person can claim many items. "Shared equally" is then just `item.total / claims.count`. `@@unique([itemId, participantId])` means a double-tap from a laggy phone can't create a duplicate claim; the database refuses it.
4. **No login, but still secure.**
   - The host gets a random `hostToken` once; we store only its hash (`hostTokenHash`), like a password. Only requests carrying the token can edit items, finalize, or mark people paid.
   - Each guest gets a `sessionToken` saved in localStorage so refreshing the page reconnects them as the same person instead of creating "Rahul (2)".
5. **The host is a Participant too** (`isHost = true`), because the host also ate. Their UPI details live on Room since they are the payee.
6. **`amountDue` is snapshotted at finalize.** After the room is finalized, the amount in a shared UPI link must never change, even if we later fix a rounding rule.
7. **Validation fields on Bill.** `hasMismatch` and `mismatchAmount` record "items add up to ₹X but printed subtotal is ₹Y" so the edit screen can show a warning. `rawAiResponse` keeps the exact AI output, which is invaluable when debugging a bad parse.
8. **`ParseStatus.FAILED` / `MANUAL`.** If the AI fails mid-demo, the host can still type items in. The app never dead-ends.
9. **`onDelete: Cascade`** everywhere: deleting a bill removes its items, room, participants and claims. No orphan rows.
10. **Indexes** on the foreign keys we query by (`billId`, `roomId`, `participantId`). Postgres doesn't index foreign keys automatically.
11. **`cuid()` IDs** instead of auto-increment numbers, so nobody can guess `/bill/2` from `/bill/1`.

### What I deliberately left out
- **User accounts / split history**: nice-to-have, a `User` model can be added later without touching these tables.
- **Weighted shares** ("I ate 2 of the 3 rotis"): could be a `shares Int @default(1)` column on Claim later. Equal sharing is the MVP spec.
